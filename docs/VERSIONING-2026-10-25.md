# Automatic product version numbering — 25 October 2026

The maintained `bash scripts/build-and-brand.sh` entry point now reserves one product version per real invocation. The first number (`build_number`) and codename are manual; the second number advances automatically. At validation, the next real build is **1.3 (Loopback)**. A two-edition invocation gives KDE and i3 the same version. Separate invocations consume separate versions.

The persistent project-root `version.json` stores the manual fields and `next_version_number`. It survives deleting `.build` and selecting another workspace. For a new larger build, manually set the first number/codename and set the next second number to 0 to begin, for example, at 2.0. See [the build guide](BUILD.md#version-numbering) for the exact JSON and rules. The counter is an integer, so 1.9 advances to 1.10.

Versions are reserved after prerequisites, fresh-output checks and signed-input verification, before starting a builder. `--check` does not consume a version or create a build workspace. Failed/partial builds after reservation consume their version; existing artifacts are retained and never relabelled. The checkout and workspace locks prevent conflicting runs. Counter writes are atomic and synced before publishing a reservation.

Immutable per-run version/codename/build-ID records are placed in both source CDs and used for ISO names/labels, OS identity and banners, installer stamp, copied GRUB labels, product RPM versions/dependencies and artifact receipts. `/usr/lib/vigilos/release.json` belongs to the identity RPM. The public evidence archive includes the release record. Fedora44 repositories, signing keys, compatibility capabilities, authentication policy and user artwork retain their existing behavior; native Qt API versions and third-party component versions are not replaced as product versions.
